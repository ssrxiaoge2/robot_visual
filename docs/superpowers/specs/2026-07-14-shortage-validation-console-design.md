# 缺料完整逻辑测试修复与独立验证控制台设计

## 1. 目标

修复现有“完整逻辑测试”页无法正确使用手工源、误启真实采样、状态不刷新和测试事件不完整的问题；新增一个独立文件实现的“缺料验证控制台”，为每个验证项提供操作步骤、预期结果和通过标准。

验证控制台是现场阶段性工具。验证完成后只隐藏第三个 Tab 入口，保留既有参数配置和自由操作测试能力，不删除或侵入缺料核心逻辑。

## 2. 总体界面结构

“缺料配置与完整逻辑测试”窗口包含三个 Tab：

1. “参数配置”：保持现有配置职责。
2. “完整逻辑测试”：作为自由操作控制台，修复输入源、状态显示和任务事件。
3. “验证向导”：只提供打开独立“缺料验证控制台”的入口和边界说明。

第三个 Tab 不直接承载验证业务界面。验证业务全部位于新建的 `ShortageValidationDialog` 中，文件固定为：

- `src/shortagevalidationdialog.h`
- `src/shortagevalidationdialog.cpp`

现有 `ShortageConfigDialog` 只负责创建入口按钮、传递非拥有的 `ShortageTestController*` 并管理验证窗口生命周期，不保存验证步骤或通过规则。

## 3. 第三个 Tab 的隐藏策略

增加一个集中定义的布尔开关，语义为“是否显示现场缺料验证入口”。开关只控制第三个 Tab 是否加入 `QTabWidget`，不编译第二套业务逻辑，也不改变测试控制器行为。

初始现场调试版本显示第三个 Tab。全部现场验证完成后，将开关改为隐藏，以下功能保持不变：

- 参数配置页正常使用。
- 完整逻辑测试页正常使用。
- `ShortageTestController` 和测试状态文件正常保留。
- 正式缺料 Engine、真实采样和主流程接线不受影响。

隐藏入口不是删除测试证据。验证结果仍保存在测试日志和现场验收记录中。

## 4. 窗口行为

### 4.1 现有缺料配置与测试窗口

现有窗口继续使用非模态 `show()`，禁止改为阻塞主窗口的 `exec()`。窗口标志明确包含最小化、最大化和关闭按钮，允许在主窗口与测试窗口之间切换。

主窗口持有一个自动失效的窗口指针：

- 第一次点击入口时创建窗口。
- 重复点击时不创建第二个窗口；如果窗口最小化则先恢复，再执行 `raise()` 和 `activateWindow()`。
- 关闭窗口后指针自动清空。
- 主窗口退出时由 Qt 父子关系安全释放窗口。

### 4.2 新缺料验证控制台

新控制台同样是非模态窗口，明确提供最小化、最大化和关闭按钮。重复点击第三个 Tab 中的入口，只恢复并激活已有控制台，不创建多个验证会话。

两个窗口都可以独立最小化和最大化。任何窗口的显示、隐藏或关闭不得启动/停止采样、修改账本或自动推进验证步骤；业务动作只能来自明确按钮。

## 5. 现有“完整逻辑测试”页修复

### 5.1 输入源状态

测试输入源仍严格二选一：

- 手工源：不访问真实 MES/PLC，只允许提交手工样本。
- 现场源：禁止提交手工样本，只允许启动和停止真实现场采样。

切换来源时执行以下规则：

- 从现场源切到手工源前先停止测试现场采样，再启用手工输入。
- 从手工源切到现场源只改变控件可用性，不自动启动采样。
- 输入源切换不清空账本、不修改正式状态。
- 启动现场采样时再次校验当前来源，避免程序化调用绕过 UI 禁用状态。

### 5.2 手工样本输入

手工源区域提供：

- 产品：88、88R、92。
- 模式：L/R、L/L、R/H。
- `actualQty`：非负 `qint64`。
- “提交手工样本”按钮。

提交时将三个输入一次性交给 `ShortageTestController::applyManualSample(...)`。输入非法时只显示中文原因，不调用 Engine。

“确认测试现场从 0 开始”与数据源无关；它只建立测试命名空间的 0 库存账本。手工源中不显示“启动现场采样”作为下一步提示，避免再次产生错误操作顺序。

### 5.3 现场采样

只有现场源选中时“启动现场采样”可用。启动成功后：

- 手工输入控件禁用。
- 输入源选择在采样停止前锁定，避免中途混用。
- 显示“等待首轮/等待第二轮稳定/稳定样本已接收/本轮拒绝”等通信状态。
- 首次稳定样本进入 Engine 后立即刷新计划和补料单。

测试现场采样继续复用唯一 `ShortageSampleCoordinator`，但稳定样本只送测试 Engine；正式 Live 未停止时仍由既有门禁拒绝启动。

### 5.4 实时状态显示

页面订阅 `ShortageTestController::snapshotChanged`，不再只使用构造时快照。每次快照更新以下内容：

- 12 工位：工位、库存、最低、最高、当前模式用量、状态、连续失败次数。
- 产品、模式、当前 `actualQty`、基线和清零候选。
- 活动工位、待补料工位顺序、严重锁定及原因。
- 当前补料单：单号、工位、来源和状态。
- 最近一次产量增量。

0 建账后首次稳定样本若库存低于最低位，页面必须显示活动工位和 `AwaitingDispatch` 补料单。由于独立测试不进入主 FIFO，此时准确文案是“测试补料单等待模拟主调度接受”，不得显示“真实硬件已补料”。

### 5.5 自由操作按钮

现有页面补齐原设计中的动作，但通过分组和状态门禁减少误操作：

- 账本与采样：0 建账、启动现场采样、停止测试。
- 测试状态：保存、重新加载、清空测试状态。
- 派单：模拟接受、模拟拒收。
- 任务事实：倒料前失败、倒料完成、倒料后失败、任务成功。
- 异常验证：重复发送倒料事件、模拟程序重启。

按钮始终可见，不使用折叠区域。当前状态不允许的动作禁用并提供中文提示，例如没有待派补料单时禁用“模拟接受”，没有运行任务时禁用“倒料完成”。业务层仍保留二次校验，不能只依赖按钮禁用保证正确性。

## 6. 独立缺料验证控制台

### 6.1 职责边界

`ShortageValidationDialog` 只负责编排验证步骤、调用测试控制器公开接口、观察只读快照和记录结果。它不得：

- 创建第二个 `ShortageEngine`。
- 直接修改 `ShortageRuntimeState`。
- 访问 `LineManager`、`TaskQueue` 或硬件控制器。
- 复制 `actualQty`、库存扣减、补料排序或任务幂等算法。
- 修改正式状态文件。

### 6.2 布局

验证控制台使用固定的三栏加底部日志布局：

- 左侧“验证项”：编号、名称、状态。
- 中间“操作步骤”：当前步骤、所需输入、预期结果、执行下一步和重新验证。
- 右侧“实际状态”：关键快照字段、自动判定结果和人工确认入口。
- 底部“验证日志”：时间、验证编号、输入、预期、实际和结果。

验证状态包括：未开始、进行中、自动通过、自动失败、等待人工确认、人工确认通过。状态枚举及每个枚举值必须有中文注释。

### 6.3 自动与人工判定边界

能够从测试快照和信号确定的结果由程序自动判定，例如库存数值、补料单状态、等待顺序和严重锁定。

涉及真实通信、窗口切换、正式文件未变化和现场设备未动作的项目，程序显示证据后等待操作员确认。不得因为 C++ 测试通过就把现场项标记为通过。

## 7. 验证项、操作步骤和通过条件

### VT-01：窗口切换能力

操作步骤：

1. 打开“缺料配置与完整逻辑测试”。
2. 分别执行最小化、恢复和最大化。
3. 切换到主窗口，再返回测试窗口。
4. 打开验证控制台并重复上述操作。
5. 连续点击两个窗口的打开入口。

通过条件：两个窗口均可最小化、最大化和恢复；主窗口始终可以激活；重复点击只激活唯一窗口，不出现多个相同窗口；窗口操作不改变测试状态。

### VT-02：测试与正式环境隔离

操作步骤：

1. 记录正式状态文件哈希、主 FIFO 数量和硬件命令计数。
2. 依次执行手工样本、现场测试采样、任务接受、倒料和失败事件。
3. 再次取得三项证据。

通过条件：正式状态文件哈希和主 FIFO 数量不变；AGV、机械臂和扫码硬件命令计数不增加；测试状态只写入 `test-*` 文件。

### VT-03：手工源不访问真实系统

操作步骤：

1. 选择手工源。
2. 选择产品 88、模式 L/R，输入 `actualQty=100`。
3. 提交手工样本。
4. 检查真实 MES/PLC 请求计数。

通过条件：测试页面接收 `actualQty=100`；真实请求计数保持不变；“启动现场采样”不可用；事件日志明确记录“手工样本”。

### VT-04：0 建账和首样本补料计划

操作步骤：

1. 清空测试状态并确认测试现场从 0 开始。
2. 选择手工源，提交产品 88、模式 L/R、`actualQty=100`。
3. 查看 12 工位表、活动工位和当前补料单。

通过条件：12 工位在建账后均为 0；首样本只建立基线、不扣库存；所有低于最低位的启用工位按同时间工位号排序；活动工位为 1；只生成一个工位 1 的 `AwaitingDispatch` 补料单；页面立即显示该状态。

### VT-05：现场源首样本补料计划

操作步骤：

1. 清空并执行 0 建账。
2. 选择现场源并启动采样。
3. 等待两轮相同产品/模式的完整有效采样。
4. 停止采样并查看补料状态。

通过条件：真实采样只在现场源启动；两轮稳定前不产生稳定样本；首次稳定样本只建基线；随后立即重评估 0 库存并显示一个 `AwaitingDispatch` 补料单；正式 Engine 和 FIFO 不变化。

### VT-06：正常产量扣减

操作步骤：

1. 在 VT-04 状态下再次提交相同产品和模式、`actualQty=105`。
2. 对照当前产品和模式的每工位用量。

通过条件：每个启用工位库存变化等于 `旧库存 - 5 × 当前模式用量`；用量为 0 的工位不变；基线更新为 105；页面显示最近增量 5。

### VT-07：派单拒绝和原单重试

操作步骤：

1. 对当前待派补料单执行“模拟拒收”。
2. 记录补料单号和状态。
3. 再执行“模拟接受”。

通过条件：拒收后补料单保持 `AwaitingDispatch`，单号不变且不增加重复补料单；接受后绑定测试专用 taskId，并依次进入 `Queued`、`Running`。

### VT-08：倒料入账与连续补料

操作步骤：

1. 对运行任务执行“倒料完成”。
2. 记录目标工位倒料前后库存。
3. 执行“任务成功”。
4. 观察是否生成下一箱。

通过条件：倒料完成时而不是任务终态时增加准确一箱；同一工位未达到最高位时生成下一箱 `AwaitingDispatch`；达到或超过最高位后释放活动工位并切换等待顺序中的下一工位。

### VT-09：倒料前失败保护

操作步骤：

1. 接受一个测试任务。
2. 连续执行配置阈值次数的“倒料前失败”，每次重新接受重试任务。
3. 查看目标工位失败次数、暂停状态和其他等待工位。

通过条件：每次倒料前失败不增加库存；达到阈值时只暂停目标工位自动补料；其他工位仍可继续计划；中文日志包含工位、原库存、失败次数和处理动作。

### VT-10：倒料后失败

操作步骤：

1. 接受任务并执行倒料完成。
2. 执行“倒料后失败”。

通过条件：已入账的一箱不回滚；倒料前失败计数不增加；补料单进入明确的倒料后失败终态。

### VT-11：重复倒料严重锁定

操作步骤：

1. 完成一次有效倒料。
2. 点击“重复发送倒料事件”。

通过条件：库存不第二次增加；系统进入严重锁定；停止新的自动补料意图；日志包含补料单号、taskId、工位和“重复倒料”处理动作。

### VT-12：`actualQty` 清零与毛刺

操作步骤：

1. 在独立重置场景依次提交 `1000→2→5`。
2. 重新验证并提交 `1000→900→500→0→2→5`。
3. 重新验证并提交 `1000→2→1005`。

通过条件：第一组按新周期累计 5 扣减；第二组连续下降期间不扣，最终合计按新周期 5 扣减；第三组将 2 判为毛刺，只按旧周期增量 5 扣减；页面显示基线和清零候选变化。

### VT-13：换型和九种组合

操作步骤：

1. 遍历 88、88R、92 与 L/R、L/L、R/H 九种组合。
2. 每次提交两轮相同上下文。
3. 在存在旧任务时提交新上下文并完成旧任务。

通过条件：一轮抖动不切换；两轮相同才确认；旧任务未终态时保存待切换上下文；旧任务排空后切换；12 工位库存数值沿用，后续扣减使用新组合用量。

### VT-14：保存、重载、清空和重启恢复

操作步骤：

1. 在无任务、等待派单和严重锁定状态分别保存并模拟重启。
2. 重新加载测试状态。
3. 执行清空测试状态。

通过条件：安全状态逐字段恢复；不安全状态显示维护锁定而不伪造任务事实；清空只删除 `test-*` 文件；正式文件哈希始终不变。

### VT-15：来源切换和误操作门禁

操作步骤：

1. 现场采样运行时尝试切换手工源和提交手工样本。
2. 停止现场采样后切换手工源并提交样本。
3. 在没有补料单、没有运行任务和没有倒料事实时检查事件按钮。

通过条件：运行中不能混用输入源；停止后可以安全切换；不满足前置状态的按钮禁用；即使直接调用控制器接口，业务层仍拒绝非法动作并输出中文原因。

## 8. 控制器接口调整

`ShortageTestController` 增加只读测试状态查询和输入源门禁所需接口，但不暴露可写 Engine：

- 发布完整快照，供两个窗口共享观察。
- 明确区分手工输入状态和现场采样状态。
- 提供当前动作可用性所需的只读结果，或由统一快照推导。
- 提供模拟重启所需的单一公共动作，复用现有保存/重建/加载流程。

现有接口的失败语义必须补全中文注释。新增变量明确说明所有权和生命周期，特别是共享采样协调器为非拥有指针、两个 Dialog 只持有非拥有测试控制器指针。

## 9. 测试设计

实施严格采用 C++17、Qt Test 和 CMake 测试先行：

- `tests/test_shortage_test_controller.cpp`：补手工/现场源门禁、首样本补料、动作可用性和模拟重启测试。
- `tests/test_shortage_dialog.cpp`：补手工输入控件、输入源切换、动态快照、按钮门禁、第三 Tab 入口和窗口标志测试。
- `tests/test_shortage_validation_dialog.cpp`：验证独立文件、15 个验证项、步骤推进、自动/人工判定、唯一窗口和隐藏入口契约。
- `tests/test_live_shortage_ui.cpp`：验证主窗口只持有一个配置测试窗口，重复打开执行恢复和置顶。

每个修复先增加失败测试并确认失败原因与现场问题一致，再写最小实现。完成后运行缺料相关测试、全量 CTest、主程序构建和 `git diff --check`。

## 10. 注释约束

实施 plan 的代码片段和实际代码必须同时满足：

- 新增或修改的 `enum class` 及每个枚举值有中文语义注释。
- 结构体和每个字段说明单位、范围、来源和用途。
- 函数接口说明参数、返回值、失败语义、副作用和线程/生命周期要求。
- 成员变量说明所有权、可空性和生命周期。
- 关键状态分支说明修改前行为、现场问题、修改后行为和不影响的既有逻辑。
- 信号连接说明唯一连接点，防止重复打开窗口导致重复处理。

## 11. 验收结论

本设计通过的必要条件为：

1. 手工源能够完整验证 `actualQty`，且真实 MES/PLC 请求为 0。
2. 现场源首次稳定样本后页面准确显示待派补料单。
3. 自由操作页覆盖原设计公开动作，并实时显示状态。
4. 独立验证控制台逐项提供步骤、预期、实际和通过条件。
5. 两个窗口都支持最小化、最大化、关闭和主窗口切换，重复入口不创建多实例。
6. 隐藏第三个 Tab 后不影响既有两页和缺料业务核心。
7. 自动测试全部通过；现场项目必须由操作员依据证据确认，不能自动冒充实机验收通过。
