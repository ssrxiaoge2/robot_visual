## 4. 名词与数据边界

### 4.1 正式库存账本

正式库存账本记录每个代码工位的当前库存、产量基线和必要恢复状态。正式运行时，上位机账本是缺料判断的事实源。

库存只有两类正常变化来源：

- MES `actualQty` 有效增量：按当前产品、模式的单件用量扣减库存。
- 真实自动或人工补料任务完成倒料：给对应工位增加一箱数量。

模拟任务、测试面板任务、任务仅入 FIFO、任务完成取料、任务完成码垛均不得改变正式库存。

### 4.2 待补料工位顺序表

待补料工位顺序表属于补料计划层，不是 `TaskQueue`。它记录已经低于最低位的工位、首次触发时间和暂停状态，用于决定下一个应补哪个工位。

### 4.3 现有 FIFO

现有 FIFO 仍由 `TaskQueue` 和 `LineManager` 管理，只保存已经被主调度接受的任务实例。新功能只允许调用明确的“追加到队尾”接口，不允许插队、重排、删除其他模块已经接受的任务。

### 4.4 补料单号与程序 taskId

- 补料单号：正式缺料模块生成并持久化的内部单调递增编号，用于跨程序重启幂等校验，不在普通工人界面展示。
- `taskId`：现有 `TaskQueue` 在单次程序运行期间生成的任务号，重启后可从 1 重新开始。
- 一个补料单号在某次运行中可以绑定一个 `taskId`；恢复后如需维护人员确认续办，可绑定新的 `taskId`，但同一补料单号最多倒料入账一次。

## 5. 配置模型与最新 Sheet3 默认值

### 5.1 36 条配置的计算方式

配置按“产品 × 代码工位”保存：

```text
3 个产品（88、88R、92） × 12 个代码工位 = 36 条配置
```

每条配置同时保存三种生产模式的用量，不是“3 产品 × 3 模式 × 12 工位 = 108 行”。UI 每个产品页签只显示 12 行，每行同时显示 L/R、L/L、R/H 三列用量。

生产模式与 PLC 位映射固定为：

- `L68` → `L/R`。
- `L69` → `L/L`。
- `L1998` → `R/H`。

- 独立完整逻辑测试已停止。

- `LineManager` 不处于 Running 或 ReturningHome。

## 6. 总体架构与对象边界

```text
                         ┌──────────────────────┐
MES / PLC ─HTTP 响应───> │ CustomSysScheduler   │
                         └───────────┬──────────┘
                                     │ 带 roundId 的协议结果
                                     v
                         ┌──────────────────────────┐
                         │ ShortageSampleCoordinator│
                         └────────────┬─────────────┘
                                      │ 完整且稳定的采样
                                      v
┌───────────────────┐       ┌───────────────────────┐
│ ShortageConfigStore│──────>│ ShortageEngine        │
└───────────────────┘       │  ├─ShortageLedger     │
                            │  └─ReplenishmentPlanner│
                            └───────┬─────────┬──────┘
                                    │         │
                            状态/审计│         │一箱补料意图
                                    v         v
                         ┌────────────────┐  ┌──────────────────────┐
                         │ShortageStateStore│ │LiveShortageCoordinator│
                         └────────────────┘  └──────────┬───────────┘
                                                       │ 只追加队尾
                                                       v
                                            LineManager / 原有 FIFO
                                                       │
                                           TaskExecutor 任务事实事件
                                                       │
                                                       └──倒料完成回到 Engine
```

核心边界：

- `ShortageConfigStore`：只负责默认配置、校验、加载、原子保存和导出。
- `ShortageSampleCoordinator`：只负责定时请求、同轮聚合、迟到响应隔离、信号三选一和两轮稳定确认。
- `ShortageLedger`：只处理库存事实和 `actualQty` 基线，不决定任务入队顺序。
- `ReplenishmentPlanner`：只管理待补料工位顺序、活动工位、补料单和失败保护，不直接操作硬件。
- `ShortageEngine`：生产态和独立测试共用的门面，按同一事务顺序调用账本、计划和持久化事件。
- `ShortageStateStore`：只负责正式或测试命名空间下的快照、备份和事件流水。
- `ShortageTestController`：拥有独立测试专用 Engine 和 StateStore，通过手工/真实输入驱动完整逻辑，不连接 `LineManager`。
- `LiveShortageCoordinator`：生产态唯一接线层，把一箱补料意图追加到现有 FIFO，并把任务事实事件回送 Engine。
- `CustomSysScheduler`：只做 HTTP/PLC 协议请求和解析，透传轮次号，不做库存和派单判断。
- `DeviceManager`：拥有生产协调器和连接关系，不实现缺料算法。
- `MainWindow`：只负责 UI 展示、确认和用户操作，不直接计算库存。

`ShortageEngine` 是进程内 `ShortageRuntimeState` 的唯一所有者。Ledger 和 Planner 都只操作 Engine 为一次事务建立的同一个状态副本：Ledger 只能修改库存、产品/模式和 `actualQty` 字段，Planner 只能修改等待顺序、活动工位、补料单和失败保护字段。事务全部校验和持久化成功后，Engine 才一次替换权威状态；禁止 Ledger、Planner 和 UI 各自保存第二份可写运行状态。

## 7. 正式账本规则

### 7.1 新建正式账本

只有客户确认“现场所有工位已清空”时，维护人员才能新建正式账本。新建后：

- 12 个工位当前库存全部为 0。
- 当前有效产品、模式尚未确认前不派单。
- 第一个完整有效采样只建立 `actualQty` 基线，不扣库存。
- 产品和模式稳定后，用量大于 0 的启用工位从库存 0 开始进入初始补料计划。
- 初始补料期间允许生产；后续 `actualQty` 增量正常扣库存，倒料完成正常加库存。

普通工人不得通过“清零”绕过恢复流程。已有有效正式账本时，默认恢复原账本，不显示一键全部清零。

### 7.2 正常产量扣减

对于有效采样：

```text
productionDelta = currentActualQty - baselineActualQty
stationConsumption = productionDelta × 当前产品/模式对应工位用量
newStock = oldStock - stationConsumption
baselineActualQty = currentActualQty
```

规则：

- `productionDelta > 0` 时扣减。
- `productionDelta == 0` 时库存、基线状态文件均不产生无意义写入。
- 用量为 0 或工位禁用时不扣减。
- 库存允许为负数，负数真实表达账本已经低于 0；不得自动截断为 0。
- 所有乘法和加减使用 64 位有符号整数，并在运算前检查溢出；溢出属于严重逻辑错误。
- 每个有效正增量都在 UI 和结构化日志中显示本轮 `productionDelta`；客户未提供现场最大合理产量前，不自行发明“巨大增量”阈值。后续如需超限告警，必须先由客户提供可验收上限，再作为可配置规则进入 spec/plan。

### 7.3 `actualQty` 清零和回退

不使用工控机 20:00 时间判断清零，因为工控机时间可能与现场不一致。只根据 `actualQty` 序列判断。

当新值小于旧基线时，保留本次回退前的 `oldBaseline`，并按以下状态机处理：

1. 不立即扣减，也不立即把旧基线覆盖为新值。
2. 第一个回退值记为 `resetCandidate`，进入“清零候选”。
3. 候选期内如果 `current < resetCandidate`，说明计数仍在向 0 回落：只把 `resetCandidate` 更新为更小值，不扣库存、不改 `oldBaseline`。
4. 候选期内如果 `current == resetCandidate`，保持等待，不写无意义状态。
5. 候选期内首次出现 `resetCandidate < current < oldBaseline`，确认发生清零：将新周期从 0 到 `current` 的累计量视为新增产量。`1000→2→5` 扣减 5；`1000→900→500→0→2→5` 先在 2 时扣减 2，再在 5 时扣减 3，合计扣减 5。
6. 候选期内如果 `current >= oldBaseline`，把低值序列视为毛刺；例如 `1000 → 2 → 1005`，只按 `1005-1000=5` 扣减。
7. 清零确认只重建产量基线，绝不清空或重算工位库存。

采样可能只看到 `1000 → 2`，而现场实际经过 `1001、1002、0、2`。当前实施边界是把确认后的 2 当作新周期从 0 开始的累计量，无法追回未采到的旧周期尾数；日志必须明确记录“可能存在最多一个采样周期的尾数误差”。该边界需在现场验收单中让客户签字确认。若客户不能接受，必须由客户提供清零信号、清零前最终计数或持续不清零计数器；仅凭离散 `actualQty` 无法消除该误差。

### 7.4 通信断线与恢复

- 某轮任何必要响应失败或超时：整轮作废，不更新库存、基线、产品、模式和补料计划。
- 断线期间已经进入原有 FIFO 或正在执行的任务继续由现有主流程安全执行；真实任务倒料完成仍必须入账。
- 断线期间不创建新的自动真实补料意图。
- 连续异常达到配置的通信报警时间后显示红色报警，但不清空状态。
- 恢复时如果产品、模式与断线前一致且 `actualQty >= 旧基线`，按差值补扣。
- 恢复时如果 `actualQty < 旧基线`，无法区分断线期间清零和数据异常，进入“恢复待维护确认”，禁止新的自动派单并提示联系维护人员。
- 客户已承诺断线期间不换产品、不换模式；如果恢复后产品或模式变化，仍按异常恢复处理，不自行猜测断线期间用量。

## 8. 采样轮次与产品/模式确认

每 15 秒默认启动一轮采样，单轮最多等待 5 秒。每轮收齐：

- 1 个 MES `actualQty` 响应。
- PLC 产品位 `L71、L72、L73`。
- PLC 模式位 `L68、L69`。
- PLC 模式位 `L1998`。

每个请求携带同一个 `roundId`。只有当前活动轮次的响应可以聚合；超时轮、已结束轮和迟到响应全部记录后丢弃，不得混入下一轮。

有效性：

- 产品位必须恰好一个为 true：L71=88、L72=88R、L73=92。
- 模式位必须恰好一个为 true：L68=L/R、L69=L/L、L1998=R/H。
- 全 false 或多个 true 均使本轮无效，并显示具体位值。
- 产品和模式组合必须连续两个完整有效轮一致后才成为稳定生产上下文。
- 稳定上下文改变时进入换型等待，不立即按新配置派单。

## 9. 换型规则

检测到新的产品或模式连续两轮稳定后：

1. 保存“待切换上下文”。
2. 停止按旧上下文创建新的自动补料意图。
3. 已经进入 FIFO、正在执行、已经倒料但仍在收尾的旧任务全部按原流程执行到终态。
4. 旧任务全部终态后，切换到新上下文。
5. 沿用 12 个工位现有库存，不清零、不按新配置追溯重算。
6. 后续产量增量和新补料判断使用新产品、模式配置。

换型期间的 5 个占位托盘由客户保证不增加 `actualQty`，程序不增加特殊排除逻辑。

## 10. 缺料触发、补满顺序与 FIFO

### 10.1 触发和停止条件

- 启用且当前用量大于 0 的工位：`库存 < 最低安全位` 时首次进入待补料工位顺序表。
- 记录第一次跌破最低位的 UTC 时间；后续继续扣减不得刷新该时间。
- `库存 == 最低安全位` 不触发。
- 活动工位每完成一次倒料增加一箱后重新判断；`库存 >= 最高安全位` 时完成该工位计划。
- 一箱倒料后超过最高位允许，不回退、不拆箱。

### 10.2 多工位顺序

待补料工位按以下稳定顺序排列：

1. 首次低位触发时间更早的在前。
2. 时间完全相同时，代码工位号较小的在前。

选中一个活动工位后采用非抢占策略：持续给该工位一箱一箱补料，直到其库存达到或超过最高位、该工位被暂停或系统进入严重锁定。其他低位工位只保存在待补料工位顺序表中，不提前全部塞入现有 FIFO。

### 10.3 一箱意图进入 FIFO 的条件

一个活动工位同时最多存在一个“尚未完成倒料”的真实任务。满足以下条件时才可生成下一箱意图：

- 正式账本和配置有效。
- 真实缺料模式已开启。
- 通信上下文有效，未处于恢复待确认或换型等待。
- 系统未严重锁定。
- 活动工位未暂停且库存仍小于最高位。
- 该工位没有尚未倒料的真实任务。
- `LineManager` 接受追加任务。

任务只能追加到 FIFO 队尾。FIFO 中已存在的模拟任务、人工任务、其他工位任务顺序完全不变。主调度拒收时保留补料意图为“等待重试”，待 `LineManager` 回到 Running 后再次尝试，不得永久卡住，也不得重复创建补料单号。

有效倒料发生后，即使当前任务还在收姿态或码垛，只要上述条件满足，同一活动工位的下一箱即可追加到 FIFO 队尾。这样既不重排 FIFO，又能持续补满当前工位。

## 11. 任务来源、人工补料与倒料入账

### 11.1 三种任务来源

现有任务来源扩展为：

- `UiMock`：模拟缺料调试任务，不改变正式账本。
- `LiveAutomatic`：正式账本自动计划生成的真实任务。
- `LiveManual`：维护或人工确认生成的一箱真实任务。

UI、日志和 FIFO 表必须用中文显示“模拟、真实自动、人工补料”。

### 11.2 12 个工位按钮复用

调度监控面板保留 12 个紧凑按钮，按钮文字仍只显示“工位1”到“工位12”，避免把库存和状态全部挤进按钮造成混乱。

- 模拟模式：标题显示“模拟缺料”，点击后保持现有模拟入队逻辑。
- 真实模式：标题显示“人工补料”，点击工位 X 后弹出二次确认，内容必须显示产品、模式、代码工位、现场位置、品号、每箱数量、当前库存、最低/最高位，并明确“将为工位 X 创建一箱人工真实补料任务”。
- 真实模式中的人工任务也追加到 FIFO 队尾，不插队。
- 自动活动工位正在连续补料时，人工补料按钮禁用，防止打断非抢占计划。
- 工位因连续倒料前失败被自动暂停时，维护人员可以在安全条件满足后创建一箱人工任务；倒料成功同样进入正式账本。
- 当前库存已达到或超过最高位时，人工补料仍需额外风险提示和再次确认，审计日志标记“高位人工补料”。

### 11.3 唯一倒料事实点

`TaskExecutor` 在 `ExecState::ArmUnload` 收到倒料阶段成功完成、切换到 `StowAfterUnload` 之前，发出一次带完整 `Task` 的倒料事实事件。该位置是物料已经进入工位、后续尚未收姿态和码垛的唯一事实点。

规则：

- 倒料前失败：本箱不入账，库存保持原值。
- 倒料后失败：保留已入账的一箱，库存不得减回。
- 模拟任务到达该点：只记录模拟任务日志，正式库存保持原值。
- 同一补料单号重复收到倒料事件：只允许第一次增加库存，后续事件必须拒绝入账并升级严重逻辑报警。
- 未知任务、任务工位与补料单工位不一致、任务来源不一致：拒绝入账并升级严重逻辑报警。

严重逻辑报警必须：打印中文错误、主界面红色显示、持久化详细事件、停止新的自动派单。正在执行的硬件任务仍按现有安全流程完成，不在缺料模块中强制打断机械臂。

### 11.4 连续失败保护

- 只统计倒料前失败。
- 同一工位默认连续 3 次倒料前失败后，暂停该工位自动补料并报警。
- 有效倒料成功立即把该工位连续失败计数清零。
- 倒料后收姿态、码垛、回站失败不增加此计数。
- 维护人员解除暂停必须填写原因并记录日志；普通工人界面只显示“联系维护人员”。

## 12. 持久化、写入频率与恢复

### 12.1 文件位置与文件组

运行文件放在可执行文件同目录的固定子目录中，正式和测试使用不同命名空间：

- 正式配置文件。
- 正式主快照。
- 正式备份快照。
- 正式追加事件流水。
- 独立测试配置/状态/备份/事件流水。

固定相对路径为：

```text
shortage-state/configuration.json
shortage-state/configuration.backup.json
shortage-state/production-state.json
shortage-state/production-state.backup.json
shortage-state/production-events.jsonl
shortage-state/test-configuration.json
shortage-state/test-configuration.backup.json
shortage-state/test-state.json
shortage-state/test-state.backup.json
shortage-state/test-events.jsonl
shortage-state/maintenance-backups/<UTC时间>-production-state.json
```

测试文件不得覆盖正式文件。配置导出由用户选择目标路径，导出文件不自动作为正式配置生效。

### 12.2 保存内容

正式状态至少保存：

- 文件格式版本、校验和、最后保存时间。
- 12 工位当前库存。
- 当前稳定产品、模式和待切换上下文。
- `actualQty` 基线、清零候选和通信恢复状态。
- 待补料工位触发时间、活动工位和暂停原因。
- 补料单号序列、补料单与当前 `taskId` 的绑定、是否已倒料入账、任务终态。
- 连续倒料前失败次数。
- 严重锁定状态和原因。

配置中的最低位、最高位、每箱数量和用量不复制成账本事实；状态记录配置版本摘要，恢复时必须校验当前配置是否与状态兼容。

### 12.3 写入频率

- `actualQty` 不变且无其他状态变化：不写。
- 一个有效变化采样：写一条紧凑流水，不按 12 个工位写 12 次。
- 完整快照最多每 60 秒一次。
- 以下关键事件立即写流水并原子保存完整快照：倒料入账、派单接受/拒绝、任务失败/终态、活动工位切换、换型确认、通信状态切换、人工操作、配置保存、严重报警和程序正常退出。

### 12.4 原子性和失败规则

- 正式/测试配置使用各自的主文件和备份文件；保存新配置前，先将当前可解析且校验合法的主配置原子写入对应备份，再用 `QSaveFile` 替换主配置。
- 加载配置时先校验主文件；主文件缺失、JSON 损坏或字段校验失败时，再尝试对应备份并明确显示恢复来源。主文件和备份都不可用时，不覆盖当前内存配置，真实模式不得启动。
- 主快照使用临时文件写入、刷新、校验后原子替换。
- 替换主文件前保留上一份有效备份。
- 每个文件包含格式版本和校验和；版本不支持或校验失败不得静默忽略。
- 运行状态恢复必须选择最新可用快照，并重放该快照 `nextAuditSequence` 之后的连续流水。顺序固定为：主快照+后续流水 → 备份快照+后续流水。流水序号缺口、重复、校验失败或重放后语义非法时，不得返回裸快照冒充最新状态，必须进入维护锁定。
- 物理倒料已经完成但持久化失败时，内存库存仍保留增加的一箱，不得回滚；立即严重报警并停止新的自动派单。

### 12.5 启动恢复界面

普通操作人员只看到两种结果：

1. “已安全恢复”：展示产品、模式、`actualQty` 基线、12 工位库存、待补料数量和未完成任务摘要；人工确认后仍需按原有 Start 启动，不自动开线。
2. “无法确认安全状态，请联系维护人员”：自动真实补料锁定，普通人员不能选择某个历史 taskId 或手工判断倒料状态。

不存在状态文件时，只能由维护人员确认“现场所有工位已清空”后新建 0 库存账本。主文件、备份和流水都无法恢复时必须锁定自动模式。

`ShortageStateStore::load()` 只负责返回带恢复来源的值对象，不能绕过 Engine 直接成为运行状态。启动接线必须按固定顺序执行：

1. StateStore 加载主/备份/流水并返回 `ShortageStateLoadResult`。
2. Engine 通过显式 `installRestoredState()` 校验配置修订号、12 工位、基线、补料单和等待顺序；全部通过后才一次替换 Engine 内部权威状态。
3. 安装恢复状态后仍保持“等待操作员确认”，不启动采样、不创建意图、不调用 `LineManager::start()`。
4. LoadResult 不安全、恢复状态校验失败或存在无法确认的 Queued/Running/Unloaded 非终态历史任务时，Engine 不安装该状态，进入维护锁定并只显示联系维护人员。

## 13. 异常库存修正

库存修正是万不得已的维护功能，不是日常生产操作。主界面工位表只读；入口为独立“异常恢复…”对话框。

允许打开和保存的条件：

- 产线已停止。
- 真实缺料监听已停止。
- FIFO 为空。
- 当前任务为空。

操作规则：

- 一次只允许修改一个工位。
- 明确显示当前库存和修改后库存。
- 必须填写原因。
- 必须输入目标工位号再次确认。
- 保存前立即备份状态。
- 保存成功写入不可省略的审计事件。
- 不提供批量修改和一键全清零。
- 全部工位重建为 0 只能走“现场已清空”的新建账本流程。

## 16. 现有模块的最小改动

### 16.1 `CustomSysScheduler`

当前分支已有的“客户系统通信测试”属于最早期临时诊断功能，已经不适配正式缺料方案。实施的第一个功能任务必须删除：MainWindow 面板和全部 `m_customSys*` 控件/槽/主题样式，`DeviceManager::Config::customSysEndpoint`、诊断调用入口和 `customSystem*` 转发信号，以及 `CustomSysScheduler` 中的 `.229` 默认地址、`DayRecord`、`defaultEndpoint()`、`testConnectivity()`、`fetchDayData()`、`connectivityChecked()`、`dayDataReady()` 等旧诊断接口。不得保留隐藏入口、兼容空壳或从 `.229` 迁移配置。

`src/customSysScheduler.h/.cpp` 文件本身不删除、不新增替代文件，而是在原文件中建立真实缺料唯一通信层。`DeviceManager` 只创建一个生产通信对象，统一命名为 `m_liveShortageScheduler`，它只连接 `ShortageSampleCoordinator`。从旧分支 `codex/v0.2.5-shortage-signals` 只按函数级移植真实缺料需要的 HTTP/PLC 协议实现；不从零重写，也不得整体 cherry-pick 旧缺料提交。

优先移植并保持协议行为的内容：

- MES `/api/MesData/day` GET 请求和 `actualQty` JSON 解析；
- PLC `/api/PlcData/GetLBitRegister` GET 请求；
- `StartAddress`、`length` 查询参数及地址范围构造；
- `PlcBitReply` 的 `success`、`timestamp`、`data/address/value` 完整校验；
- `RequestContext`、`roundId` 原样透传以及 `mesReplyReady`、`plcReplyReady` 信号；
- 网络错误、非 2xx、JSON 错误、缺字段、重复地址和字段类型错误的中文诊断；
- 真实缺料 MES 默认地址使用 `.228` 基线，只从缺料配置文件读取；PLC URL 从该 MES URL 的 scheme/host/port 派生；代码、UI 和当前配置中不再存在 `.229` 旧入口。

移植时必须调整的内容：

- 旧代码固定 3 秒 HTTP 超时改为与当前“单轮超时”配置一致，默认 5 秒；
- 真实缺料 MES 回复类型使用 `qint64 actualQty`；旧 `DayRecord` 类型直接删除，不提供类型兼容。
- 协议层只发出原始成功/失败结果，不保存稳定产品、模式、库存或任务；
- `DeviceManager` 中只允许一个 `CustomSysScheduler` 实例和一套到 `ShortageSampleCoordinator` 的真实信号接线。

函数级移植前必须先增加失败的 C++ 删除契约和协议契约测试；删除契约证明旧 UI/API/`.229` 标识已经消失，协议契约逐项对照旧缺料分支输入输出。两类测试全部通过后才允许接入 `ShortageSampleCoordinator`。

### 16.2 `TaskExecutor`

只在 `ArmUnload` 成功完成、进入 `StowAfterUnload` 前增加一次 `materialUnloaded(Task)` 信号。不得修改机械臂动作顺序和失败恢复逻辑。

### 16.3 `LineManager`

- 保留 `reportShortage(int)` 作为模拟入口。
- 新增可返回接受结果和 `taskId` 的真实任务追加接口。
- 转发任务开始、倒料完成、任务成功、任务失败、系统级错误/取消等事实。

## 17. 错误分级

| 级别 | 示例 | 行为 |
| --- | --- | --- |
| 输入/单轮错误 | 响应超时、位非三选一、JSON 字段错误 | 作废本轮，说明原因，不改变账本 |
| 配置错误 | 最高位不大于最低位、重复映射、每箱为 0 | 禁止真实模式，配置页定位到单元格 |
| 工位暂停 | 连续达到阈值的倒料前失败 | 只暂停该工位自动任务，报警，可由维护人员处理 |
| 严重锁定 | 重复倒料、未知任务、工位不匹配、溢出、关键持久化失败 | 红色报警，停止所有新自动派单，现有硬件任务安全完成，联系维护人员 |

所有错误都必须写中文日志。不得用“库存不增加”“库存不回滚”等可能混淆时间点的短句代替明确描述；必须写成：

- “本箱在倒料前失败，库存保持事件发生前的数值。”
- “本箱已经完成倒料并增加一箱，后续失败不得把这一箱从库存中减回。”
