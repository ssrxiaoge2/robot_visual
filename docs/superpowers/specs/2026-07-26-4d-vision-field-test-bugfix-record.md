## 1. 记录目的

4D 联合视觉对准逻辑完成后，现场将最大联合精修次数设置为 2 进行了多轮实机测试。测试表明：

1. 部分任务能够在一至两次联合精修内完成抓取；
2. 部分任务出现 Rz 正负往复变化；
3. 部分任务的 XY/Rz 已进入阈值，但 Z 三帧极差始终无法满足原条件；
4. 有一次任务因锁定目标单帧丢失而立即停止。

本记录用于说明三个问题的现场证据、讨论过程、最终决策、实际代码改动和待验证事项，避免只保留代码而缺少问题追溯。

## 2. 现场结果概览

最大联合精修次数为 2 的八轮测试中：

| 分类 | 次数 | 说明 |
|---|---:|---|
| 成功 | 4 | 其中两轮使用了第二次联合精修 |
| Rz 往复变化后次数耗尽 | 2 | 出现 `+24° → -8° → +6°` 一类变化 |
| XY/Rz 已满足但 Z 未稳定 | 1 | 平面残差满足阈值，Z 原始三帧极差未在 8 秒内持续满足 |
| 锁定目标暂时丢失 | 1 | 视觉仅保留旁站候选，上位机拒绝切换并停止 |

本轮没有通过放宽 XY/Rz 阈值、增加精修次数或延长 8 秒窗口来提高表面成功率。

## 3. Rz 往复变化

### 3.1 现场证据

典型过程包括：

```text
+24.25° → 下发 -24.25° → -8.13°
+23.96° → 下发 -23.96° → -7.77°
+17.14° → 下发 -17.14° → -5.40°
+17.97° → 下发 -17.97° → -6.71°
```

Rz 在修正后越过零点，说明当前方向并非简单取反错误，但修正量、旋转中心、视觉角度响应或工具坐标关系仍可能存在系统误差。

### 3.2 补充现场条件

当前尚未完成“夹爪抓取中心到机械臂末端”的 TCP 标定，现有代码主要通过 Z 余量补偿夹爪长度。该做法不能覆盖：

- 夹爪中心相对末端的 X/Y 偏心；
- 实际工具 Z 轴方向误差；
- 绕 Rz 旋转时的真实抓取中心偏移；
- 新 TCP 与 C++ 手眼矩阵工具坐标系不一致。

现场还观察到：料箱相对夹爪较正、所需 Rz 旋转较小时，通常更容易满足 XY/Rz 阈值。该现象与“大角度旋转放大错误 TCP 旋转中心带来的 XY 耦合”一致，但不能据此认定 TCP 是唯一原因。

### 3.3 最终决策

当前不修改 Rz：

- 不加入临时 `0.75` 修正系数；
- 不放宽 Rz 阈值；
- 不增加联合精修次数；
- 不修改 Python 角度算法。

先完成夹爪抓取中心 TCP 标定，并确认新 TCP 与 C++ 手眼矩阵使用同一工具坐标系。标定后重新采集“精修前视觉 Rz、下发工具 Rz、运动前后实际 TCP、运动后稳定视觉 Rz”，再判断是否需要角度比例补偿。

## 4. XY/Rz 已满足但 Z 无法稳定

### 4.1 原逻辑

每个联合 MoveJ 或 MoveL 到位后：

```text
最少观察 4 秒
最多观察 8 秒
只接收 frame_id 和 timestamp 严格递增的真实新帧
最近 3 个真实 Z 样本最大值减最小值不大于 5mm
```

该规则对连续单帧深度异常较敏感。只要最近三帧中混入一个高异常值或低异常值，本次窗口就不能判稳。

### 4.2 失败样本

现场失败轮次在约 4.56 秒时，最近五个真实 Z 样本为：

```text
[947.0, 943.5, 942.1, 934.4, 948.7] mm
```

五帧排序后：

```text
[934.4, 942.1, 943.5, 947.0, 948.7] mm
```

去掉一个最低值和一个最高值后：

```text
[942.1, 943.5, 947.0] mm
```

核心三帧极差为：

```text
947.0 - 942.1 = 4.9mm
```

核心结果已经满足原 5mm 稳定边界，但原“最近连续三帧原始极差”会被两端异常值反复打断，最终在 8 秒处停止。

### 4.3 最终修复

新的 Z 判稳规则为：

```text
保留最近 5 个真实新帧
→ 对 Z 排序
→ 去掉一个最大值和一个最小值
→ 中间 3 帧核心极差不大于 5mm
→ 使用 5 帧中值作为最终下探深度
```

保持不变的安全边界：

- 最少观察时间仍为 4 秒；
- 最大观察时间仍为 8 秒硬上限；
- 核心稳定极差仍为 5mm，没有直接放宽；
- 重复 HTTP 缓存帧仍不计入样本；
- XY/Rz 必须同时满足运行时阈值；
- 目标必须仍然有效；
- Z 下探方向、抓取余量和硬上限公式保持不变。

### 4.4 日志变化

统一窗口日志由：

```text
ZRange=...
```

调整为：

```text
ZCoreRange=...
ZMedian=...
ZSamples=[...]
```

现场可以同时判断原始五帧、核心极差和最终采用的中值。

## 5. 锁定目标暂时丢失

### 5.1 现场证据

故障帧中，上一锁定锚点约为：

```text
(-45.4, 215.5) mm
```

下一帧仅剩一个候选，其锁定距离约为：

```text
372.9mm
```

该候选明显不是上一锁定目标。C++ 拒绝切换到旁站目标并停止调度，避免抓取错误工位目标。

### 5.2 能力边界

当前 C++ 所谓“锁定”是基于工位锚点、层高和距离的候选关联，不是真正的视觉追踪器。目标不再出现在 Python 检测结果中时，上位机无法凭空恢复其位置，也不能证明后续重新出现的候选仍是同一个物体。

曾讨论过“允许临时丢失若干帧并继续原 4～8 秒窗口”，但该策略会带来以下问题：

- 可能混用目标丢失前后的 Z 稳定证据；
- 可能使用历史坐标掩盖视觉算法漏检；
- 没有稳定 `track_id` 时无法证明重新出现的是同一个目标；
- 增加上位机冗余状态，却没有修复视觉端根因。

### 5.3 最终决策

当前版本保持原安全行为：

```text
ValidateVisionAlignment 状态内锁定目标丢失
→ 立即停止视觉等待
→ 通过统一错误出口停止调度
→ 不下发精修
→ 不下探
→ 不切换旁站目标
→ 不自动重试
```

不在本轮增加上位机丢帧等待策略。

### 5.4 远期视觉方案

更换新工控机并提升 Python 帧率后，再评估真正的目标追踪器。建议视觉接口至少提供：

```text
track_id
track_state
lost_frames
frame_id
timestamp
目标位置、深度、角度和置信度
```

机械臂静止的观察窗口内由 Python 维护目标 ID；跨机械臂运动阶段仍需结合固定工位锚点或机器人位姿补偿，不能只依赖图像像素位置关联。

## 10. Rz 故障与 TCP、手眼标定问题的关系

### 10.1 原始问题与引申问题

本次 TCP 和手眼标定讨论不是独立新增需求，而是从现场 Rz 往复故障继续追查得到的坐标链问题。

原始现场问题为：

```text
Rz 调整角度较大
→ 修正后 Rz 越过零点或反向残留
→ XY 与 Rz 难以同时稳定进入阈值
→ 两次联合精修用完后停止
```

同时存在以下对照现象：

```text
料箱相对夹爪本来比较正
→ 所需 Rz 旋转较小
→ XY/Rz 通常更容易同时满足阈值
→ 抓取成功率明显更高
```

继续检查发现，目前机器人使用的原有 `TCP` 位于法兰末端，夹爪抓取中心尚未完成 TCP 标定，代码主要通过 Z 数值补偿夹爪长度。由此形成一个高优先级根因假设：

```text
机器人实际绕法兰中心执行 Rz
而视觉和抓取希望绕夹爪抓取中心执行 Rz
→ 夹爪中心存在 X/Y 偏心或工具方向误差时
→ Rz 转角越大，夹爪中心附带的 XY 位移越明显
→ 视觉表现为 Rz 修正后 XY 又被带偏
```

该现象与现场结果一致，但当前证据还不足以证明 TCP 是唯一根因。还需要排除：

- 手眼矩阵误差；
- 视觉角度估计误差；
- Python 流水线旧帧；
- `HRIF_WayPointRel` 工具坐标语义；
- 夹爪机械安装偏心或松动；
- 大角度下箱体角度存在 90° 等价歧义。

因此，当前正确处理不是立即修改 Rz 比例，而是先建立一致的真实工具坐标链，再使用同一批现场工况复测。

### 10.2 本轮结论边界

当前已经确认：

1. 需要标定真实夹爪抓取中心 TCP；
2. 新 TCP 不能继续使用控制器中锁定的原有名称 `TCP`，需要创建新的 TCP 名称；
3. 所有示教器 `Func_*` 中包含运动的节点，必须人工逐个选择新 TCP；
4. C++ 上位机直接下发运动时使用的 TCP 名称也必须改为新 TCP；
5. Python 手眼标定程序当前不主动选择 TCP，仅读取 Modbus 位姿；
6. 在确认 Modbus `1036` 的原点语义后，使用新 TCP 重新完成手眼标定；
7. 标定和验证过程中继续保留 4D，不在本轮引入 Rx/Ry 自动修正。

当前尚未确认：

1. Modbus `1036 Actual_PCS_Base` 的位姿原点是法兰还是当前激活 TCP；
2. 新夹爪 TCP 的最终名称和六维标定结果；
3. TCP 标定完成后，Rz 大角度是否仍会引起 XY/Rz 往复；
4. 现有 Z 补偿中哪些属于旧 TCP 长度补偿，哪些属于必要的抓取工艺余量。

## 11. 控制器 TCP 和示教器程序的现状

### 11.1 原有 TCP

当前控制器中的原有 `TCP` 位于法兰末端，六维偏移为零，并且原名称不能直接改成新夹爪 TCP。后续需要：

```text
保留原有 TCP 不变，作为备份和回退基准
→ 新建一个独立命名的夹爪 TCP
→ 使用控制器 TCP 标定功能得到真实抓取中心
→ 将新夹爪 TCP 设置为当前 TCP
```

文档暂不固定新 TCP 名称。示教器、C++ 和现场操作规程最终必须使用完全相同的名称，不能一处写 `TCP_1`、另一处仍使用 `TCP`。

### 11.2 当前 TCP 与点动页面

现场已经确认：

```text
在 TCP 配置页面选择并保存“当前 TCP”
→ 点动页面的 TCP 会自动同步切换
→ 点动页面不需要再次手工选择
```

该行为说明控制器存在全局“当前激活 TCP”。但是，全局当前 TCP 的联动不能代替示教器程序节点中的 TCP 检查。

### 11.3 `Func_*` 中的运动节点

示教器 `Func_*` 中的 MoveJ/MoveL 节点保存了自己的 TCP 配置。C++ 调用 `HRIF_RunFunc` 时只传递函数名和参数，不会替示教器批量改写节点 TCP。

现场已经确定：

```text
所有 Func_* 中包含运动的节点
→ 人工逐个选择新的夹爪 TCP
→ 不允许遗留使用原有 TCP 的运动节点
```

检查范围不能只覆盖拍照函数，还应包括：

- 拍照位函数；
- 抓取和夹紧衔接函数；
- 过渡位函数；
- 收拢和复位函数；
- 倒料函数；
- 码垛基准和释放函数；
- 其他通过 `HRIF_RunFunc` 调用的运动函数。

### 11.4 “使用关节角度”的现场验证

现有 `Func_*` 多数使用 MoveJ，但没有勾选“使用关节角度”。现场已经确认，在当前零偏 TCP 条件下，同一个点勾选和不勾选时显示的 J1～J6 完全一致。

该结果证明当前保存的关节值与现有点位一致，但不能直接证明换成非零夹爪 TCP 后，未勾选的笛卡尔点仍会保持原机械臂姿态。原因是：

```text
未使用关节角度
→ 控制器优先保持节点保存的笛卡尔目标
→ TCP 从法兰零点改为夹爪中心后
→ 为让新 TCP 到达旧笛卡尔坐标，控制器可能改变关节姿态

使用关节角度
→ 控制器按保存的 J1～J6 到位
→ 原拍照位的机械臂和相机物理姿态更容易保持不变
→ 页面显示的 TCP 笛卡尔坐标会随新 TCP 定义发生变化
```

因此，固定拍照位和固定过渡位应先选一个函数进行试点：

1. 备份原程序和点位；
2. 记录原 J1～J6、法兰位姿、相机物理位置和周边间隙；
3. 节点选择新夹爪 TCP；
4. 对需要保持原物理姿态的固定 MoveJ 点，低速测试“使用关节角度”；
5. 确认 J1～J6、相机视野和现场安全间隙保持正确；
6. 试点通过后再逐个迁移其他固定 MoveJ 节点。

MoveL、相对工具运动以及确实需要保持笛卡尔终点的节点不能机械地全部切换成关节目标，必须按节点用途单独验证。

## 12. C++ 上位机需要处理的 TCP

### 12.1 直接下发运动

`src/huayanScheduler.cpp` 当前存在：

```cpp
static const QString kTcpName = QStringLiteral("TCP");
```

该名称被直接传给：

- `HRIF_MoveJ`；
- 首次视觉联合对准使用的 `HRIF_WayPoint`；
- 联合精修使用的 `HRIF_WayPointRel`。

因此，仅在示教器页面把新 TCP 设置为当前 TCP，不足以保证 C++ 直接运动使用新 TCP。后续 C++ 必须把 `kTcpName` 改成与控制器中新夹爪 TCP 完全一致的名称，或者在后续方案中改成可校验的统一配置。本轮文档只记录要求，不实施代码修改。

### 12.2 通过 `Func_*` 执行的运动

C++ 调用 `HRIF_RunFunc` 时不传 TCP 名称。该类运动最终使用哪个 TCP，由对应示教器函数内部的运动节点决定。

两条路径必须同时迁移：

| 运动来源 | TCP 的决定位置 | 后续处理 |
|---|---|---|
| C++ 直接调用 `HRIF_MoveJ`、`HRIF_WayPoint`、`HRIF_WayPointRel` | `kTcpName` | C++ 改为新夹爪 TCP 名称 |
| C++ 调用 `HRIF_RunFunc` | 示教器 `Func_*` 内部节点 | 人工逐节点选择新夹爪 TCP |

只改其中一条会形成混合坐标链。例如拍照函数使用新 TCP，但视觉精修仍传旧 `TCP`，机器人就可能在同一轮任务中切换旋转中心。

## 13. Python 手眼标定程序的处理边界

### 13.1 当前程序行为

手眼标定程序：

- 不传递 TCP 名称；
- 不调用机器人 SDK 设置当前 TCP；
- 通过 Modbus TCP 读取 `1036 Actual_PCS_Base`；
- 将六维位姿直接作为标定输入；
- 在界面和计算中将该位姿称为工具或末端位姿。

因此，从“新 TCP 名称”这一点看，Python 当前不需要增加 `TCP_1` 或其他名称配置。标定前由示教器将新夹爪 TCP 设置为当前 TCP，并在整套采集期间保持不变。

### 13.2 Modbus 数据表能够确认的内容

《modbus slave数据表20250520》明确列出：

| 地址 | 字段 | 数据表说明 |
|---:|---|---|
| 1012 | `Actual_Position_PCS` | 当前空间坐标值 |
| 1024 | `Actual_PCS_TCP` | TCP 坐标系下的空间坐标值 |
| 1036 | `Actual_PCS_Base` | Base 坐标系下的空间坐标值 |

该数据表能够确认 `1036` 使用 Base 坐标系表达，但没有明确说明该六维位姿的原点究竟是法兰中心还是当前激活 TCP 中心。“Base 坐标系下”只说明表达坐标系，不能单独证明位姿原点是法兰。

### 13.3 必须执行的静止切换测试

在真正进行手眼标定前，执行：

```text
机器人保持静止，J1～J6 不动
→ 使用原有零偏 TCP，读取并记录 1036
→ 切换到已经标定、具有明显非零偏移的新夹爪 TCP
→ 不移动机器人，再读取并记录 1036
→ 比较两次六维位姿
```

当前截图中的 `TCP_1` 六项仍为零，与原法兰零点 TCP 等价，不能用于该测试。必须使用完成标定后的非零 TCP。

结果解释：

```text
1036 随 TCP 切换发生变化
→ 1036 表示当前激活 TCP 在 Base 下的位姿
→ Python 地址继续使用 1036
→ 手眼标定期间必须始终激活新夹爪 TCP
→ 标定结果可按“相机到新夹爪 TCP”理解

1036 在 TCP 切换后完全不变
→ 1036 更可能表示法兰在 Base 下的位姿
→ 当前 Python 中“工具/法兰”的命名和变换语义需要重新核对
→ 不得直接把结果当成相机到新夹爪 TCP
→ 应明确加入法兰到夹爪 TCP 的刚体变换后再继续
```

在测试结论出来前，不修改 Python 的 Modbus 地址，也不把“Python 一定无需修改”写成无条件结论。

## 14. 手眼标定是否需要重新进行

### 14.1 当前决策

后续建立真实夹爪 TCP 后，重新采集整套手眼标定数据，不复用当前矩阵直接上线。

原因不是相机物理位置发生了变化，而是生产系统将工具参考点从法兰零点切换为真实夹爪抓取中心。C++ 当前使用的手眼矩阵、机器人返回的工具位姿和运动接口中的 TCP 必须属于同一条坐标链。

目标链路应统一为：

```text
相机测量
→ C++ 手眼矩阵转换到新夹爪 TCP
→ 新夹爪 TCP 下计算视觉修正
→ C++ 使用同名新 TCP 下发 MoveJ/MoveL
→ 示教器 Func_* 也使用同名新 TCP
```

### 14.2 拍照位不必全部重新示教的条件

更换 TCP 后，点位页面显示的 X/Y/Z/Rx/Ry/Rz 会发生变化是正常现象，因为同一机械臂关节姿态下，新 TCP 的空间坐标与法兰零点坐标不同。

对于固定拍照位，如果通过关节目标保持原 J1～J6，则：

- 机器人本体姿态不变；
- 相机物理位置和视角不变；
- 原工位拍照安全空间不变；
- 不必因为坐标显示变化而重新寻找拍照位置；
- 仍需逐工位低速复核相机画面、焦距、视野和周边间隙。

因此，预期工作重点是“迁移节点 TCP、确认关节目标和重新手眼标定”，而不是把所有固定拍照位从零开始重新示教。

## 15. Z 补偿的处理原则

真实夹爪 TCP 标定后，不能立即把所有代码 Z 参数统一删除。需要先区分两类含义：

### 15.1 应当取消或重新计算的旧 TCP 补偿

如果某个 Z 数值只是为了弥补“原 TCP 在法兰、没有包含夹爪长度”，那么新 TCP 已经包含该几何关系，继续保留会产生重复补偿。此类补偿应在实测后取消或归零。

### 15.2 必须继续保留的工艺和安全参数

以下内容不等同于 TCP 长度，不能因为标定新 TCP 而删除：

- 预抓取安全高度；
- 抓取插入深度；
- 箱口到夹紧位置的工艺余量；
- 释放高度；
- Z 最大下探硬上限；
- 防撞和异常深度保护。

正确顺序是：

```text
完成真实 TCP 标定
→ 确认手眼坐标链
→ 暂时保持工艺保护
→ 低速、禁止自动夹紧条件下测量实际 TCP 下探结果
→ 识别并移除重复的夹爪长度补偿
→ 保留并重新核对工艺余量和安全上限
```
