# 充电统一一键安全预检设计

## 一、背景与目标

当前软件首次启动后，充电桩尚无完整安全快照，
`ChargePileController::shutdownRequired()`会保守返回真。因此手动充电必须先点
“查询状态（只读）”再点“开始充电”；自动充电授权也可能因为缺少安全快照而
无法开启。

本次目标不是简单隐藏一次按钮操作，而是统一三个不同时间点的安全责任：

1. 手动开始充电时，自动取得本次操作前的充电桩安全快照。
2. 开启自动充电授权时，确认当前不存在未管理的输出、机械动作或恢复上下文。
3. 主调度真正准备自动充电时，再次取得紧邻DO0置高之前的新安全快照，不能复用
   数小时前的授权快照。

## 二、范围约束

- 不新增生产类，不新增界面控件，不改变现有按钮布局。
- 不把异步业务续接放入MainWindow。
- 不把AGV DO0并入ChargePileController，保持AGV与充电桩通信解耦。
- 不改变自动充电阈值、FIFO、任务执行、返航和双阈值停止策略。
- 不删除充电桩控制器内部原有启动前完整预检、参数写入后复检、E11处理和安全
  收尾。
- 任何预检查询都只读；查询明确安全前不得置高DO0，不得发送充电桩Start。
- 不自动重试设备安全失败。

## 三、方案比较

### 方案一：DeviceManager统一持有预检意图（采用）

DeviceManager保存唯一待处理预检意图，并统一消费
`ChargePileController::queryFinished`。查询成功后根据意图重新校验业务条件，
再进入自动授权或现有DO0启动入口。

优点是手动、自动授权和主调度实际启动共用同一串行边界；普通查询不会误启动，
MainWindow和AutoChargeCoordinator仍只表达用户操作或调度意图。

### 方案二：各调用方自行监听查询结果

由MainWindow处理手动和自动开关，由AutoChargeCoordinator处理自动启动。代码
表面分散较少，但同一个`queryFinished`会存在多个所有者，容易把普通查询、启动
查询和启动恢复查询串线，不采用。

### 方案三：ChargePileController直接协调DO0

把查询、AGV DO0和充电桩Start放进同一控制器。这样会让充电桩通信类反向依赖
AGV，破坏当前设备解耦和唯一寄存器所有权，不采用。

## 四、统一预检意图

DeviceManager只增加一个轻量枚举，不新增协调器：

```cpp
enum class ChargePreflightIntent {
    None,
    ManualStart,
    EnableAutomatic,
    AutomaticStart
};
```

任何时刻最多存在一个预检意图。已有查询、DO0操作、充电会话或应用关闭在途时，
新的预检意图同步拒绝。

## 五、手动开始时序

1. 操作人员点击“开始充电”，沿用现有现场安全确认对话框。
2. DeviceManager先校验主调度Idle、AGV快照有效、AGV位于LM1、导航已停止、
   自动模式关闭、没有自动会话、控制器非忙碌且不是`Unknown/Fault`。
3. 保存`ManualStart`意图并执行一次新的完整只读查询，不复用旧快照。
4. 查询成功后清除意图并重新执行第2步校验，防止查询期间条件变化。
5. 只有控制器进入`SafeComplete`且`shutdownRequired()==false`时，才进入现有
   `requestChargeStartWithDo0(Manual)`。
6. 查询失败或状态不安全时不设置DO0，通过现有界面提示具体原因；主调度原本为
   Idle，不进入Error。

## 六、自动授权时序

1. 用户打开“自动充电”开关时，开关尚不视为已经授权。
2. DeviceManager校验控制器非忙碌、没有活动会话、状态不是`Unknown/Fault`，
   保存`EnableAutomatic`意图并执行完整只读查询。
3. 查询明确安全后重新校验，才调用`AutoChargeCoordinator::setEnabled(true)`。
4. 查询期间界面显示正在确认安全；授权成功后开关才保持打开。
5. 查询失败、状态不安全、应用关闭或用户条件变化时，开关恢复关闭并提示原因。
6. 自动授权失败不改变已有主调度状态，保证“自动功能未成功开启时不影响原调度”。

此处查询建立的是“允许进入无人干预策略”的当前安全基线，不替代以后真正开始
充电前的新查询。

## 七、主调度自动开始时序

1. AutoChargeCoordinator沿用现有低电、任务完成、派单保持、返回LM1及导航停止
   判断，发出`automaticChargeStartRequested`。
2. DeviceManager不立即置高DO0，而是保存`AutomaticStart`意图并执行一次新的
   完整只读查询。协调器的`startIntentPending`在查询期间保持，防止重复请求。
3. 查询完成后重新校验：
   - 自动授权仍然开启；
   - 主调度仍处于允许运行自动策略的状态；
   - AGV快照仍有效、仍位于LM1且导航已经停止；
   - 控制器明确`SafeComplete`且无需安全恢复。
4. 通过后调用现有`requestChargeStartWithDo0(Automatic)`；DO0确认高且充电桩
   真正接受会话后，才向协调器反馈启动成功。
5. 查询期间协调器既有派单保持继续有效，不允许队列任务绕过低电充电需求。

## 八、失败分类与主调度处理

### 8.1 设备安全失败

以下情况属于设备安全失败：

- 充电桩连接、响应、协议或完整快照查询失败；
- 充电桩仍在工作、继电器吸合、电流不安全或推杆状态不安全；
- 控制器仍有未完成或结果不确定的安全恢复上下文。

若意图为`AutomaticStart`：

1. 不置高DO0，不发送充电桩Start。
2. 向AutoChargeCoordinator反馈本次启动未接受。
3. 保持“禁止派单”的安全效果；进入Error后由主调度自身门禁接管，自动充电
   `hold`电平仍按现有Error逻辑释放，避免两套门禁互相覆盖。
4. 通过LineManager现有外部错误入口让主调度进入Error，并显示需要人工处理的
   明确原因。
5. 不自动查询或重试，避免持续操作故障设备。

人工检查并通过现有“查询状态”或“停止充电”完成安全恢复后，使用主调度现有
停止/复位操作解除Error；人工重新启动主调度后才重新评估自动充电。

### 8.2 条件取消

查询期间发生下列情况只取消本次意图，不进入Error：

- 操作人员关闭自动充电；
- 操作人员停止主调度或应用开始关闭；
- AGV不再位于LM1或导航状态不再允许启动；
- 自动授权、主调度状态等业务条件不再成立。

条件取消仍不得置高DO0或发送Start。后续是否再次申请由新的用户动作或主调度
输入变化决定。

## 九、查询结果隔离

- 普通“查询状态（只读）”不设置预检意图，只更新界面。
- 软件启动时DO0遗留高电平触发的充电桩查询继续使用独立标志，不能消费预检意图。
- 每个查询结果只由创建它的意图消费一次；消费前先清除意图，防止同步信号重入。
- 应用关闭优先级最高，会清除未完成意图；迟到结果不能启动DO0。

## 十、界面反馈

- 不新增控件。
- 手动预检期间沿用现有充电阶段与日志显示；失败时显示“手动充电被拒绝”。
- 自动授权预检期间提示“正在确认充电桩安全”，开关不提前表示授权成功。
- 自动实际启动的设备安全失败通过主调度Error、充电决策文本和日志同时提示。

## 十一、自动化测试

至少覆盖：

1. 三种意图均发起新的完整只读查询，查询前DO0和充电桩Start计数为0。
2. 三种意图只有在`SafeComplete`且无需恢复时才能继续。
3. 手动成功进入`requestChargeStartWithDo0(Manual)`。
4. 自动授权成功后才设置协调器Enabled。
5. 自动实际启动成功进入`requestChargeStartWithDo0(Automatic)`，启动回执只
   发布一次。
6. 自动实际启动的设备安全失败保持禁止派单效果并触发一次主调度Error。
7. 主动关闭、Stop、应用关闭和LM1条件变化只取消，不触发设备故障Error。
8. 普通查询和DO0启动恢复查询不消费预检意图。
9. 既有DO0、充电控制器、E11、关闭安全、自动协调器和主调度旁路测试全部通过。

## 十二、现场验收

1. 软件重启后不手动查询，点击一次“开始充电”可自动查询并在安全时继续。
2. 软件重启后打开自动充电，自动完成授权前查询；失败时开关保持关闭且不影响
   原主调度。
3. 主调度低电返回LM1后，实际启动前再次出现一轮只读查询，查询完成前DO0保持低。
4. 自动实际启动查询失败或状态不安全时不置高DO0、不发送Start，主调度进入
   Error且不自动重试。
5. 查询期间主动关闭自动功能或Stop只取消，不误报设备故障。
6. 成功流程每次只产生一次DO0置高意图和一次充电桩正常Start命令。
