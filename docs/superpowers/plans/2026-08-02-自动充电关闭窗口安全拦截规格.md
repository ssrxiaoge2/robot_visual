# 自动充电关闭窗口安全拦截规格（2026-08-02）

## 问题陈述

在 `robot_visual` 项目中，自动充电逻辑和关闭窗口安全拦截绑定过紧。

当主调度没有开启自动充电逻辑，且系统没有进入过手动充电、自动充电、DO0 打开、自动会话等真实充电责任时，仅因为充电控制器缺少 `SafeComplete` 安全基线，关闭窗口就会持续请求安全意见或阻止退出。这会让现场操作员误以为设备处于实际危险状态，也会干扰正常关闭流程。

但关闭保护本身不能被简单放宽：如果系统确实存在手动充电、自动充电、DO0 打开、自动会话未安全释放，或者控制器已经明确进入 `Fault` / `Unknown`，关闭窗口仍必须拦截或要求人工接管。

## 解决方案

引入“关闭窗口专用”的充电安全拦截判断。

关闭窗口时，不再直接使用充电控制器的通用停机判断作为唯一依据，而是由设备管理层结合当前业务上下文判断：

- 如果存在真实充电责任，继续拦截关闭窗口。
- 如果控制器明确处于 `Fault` / `Unknown`，继续拦截关闭窗口。
- 如果只是“缺少安全基线”，但没有任何实际充电责任，且自动策略没有参与主调度，则不拦截关闭窗口。
- 保持充电控制器自身的保守安全语义不变。

本方案的核心不是“关闭自动充电就放行一切”，而是区分：

- 没有实际充电责任，只是缺少安全基线。
- 已经存在设备安全事实未证明的真实责任。

前者可以不拦截关闭窗口，后者仍必须拦截或要求人工接管。

## 用户故事

1. 作为现场操作员，我希望未开启自动充电时可以正常关闭窗口，以免被无实际风险的安全提示阻塞。
2. 作为现场操作员，我希望系统只有在确实存在充电安全责任时才拦截关闭窗口，以便我能区分真实风险和普通退出。
3. 作为现场操作员，我希望手动充电已经参与后，关闭窗口仍然被安全保护，以免设备处于未证明安全状态。
4. 作为现场操作员，我希望自动充电会话未安全释放时关闭窗口被拦截，以免退出程序掩盖设备风险。
5. 作为现场操作员，我希望 DO0 已经处于打开或激活状态时关闭窗口被拦截，以免机构动作未收尾。
6. 作为现场操作员，我希望应用关闭收尾正在进行时继续拦截关闭窗口，以免重复关闭造成流程中断。
7. 作为维护人员，我希望 `Fault` / `Unknown` 状态不因为自动充电开关关闭而被忽略，以免真实故障被误放行。
8. 作为维护人员，我希望历史残留上下文、重启重连后的异常状态仍能触发安全保护，以便现场按设备事实处理风险。
9. 作为维护人员，我希望普通只读查询不会被当成真实充电责任，以免仅查看状态也导致关闭窗口被持续拦截。
10. 作为维护人员，我希望启动轻量查询不会被当成真实充电责任，以免初始化阶段缺少安全基线时误阻塞关闭窗口。
11. 作为维护人员，我希望预检尚未进入 DO0 打开或激活时可以取消意图并关闭窗口，以免未执行动作也被当成充电中。
12. 作为维护人员，我希望预检的迟到结果不能继续启动 DO0 或充电动作，以免窗口关闭意图之后又触发设备动作。
13. 作为开发人员，我希望关闭窗口的判断规则集中在设备管理层，而不是散落在 UI 层。
14. 作为开发人员，我希望充电控制器的通用停机判断保持保守，不因为窗口关闭场景而被削弱。
15. 作为开发人员，我希望有纯规则函数表达关闭拦截规则，以便用单元测试覆盖规则表。
16. 作为测试人员，我希望能覆盖“仅缺少安全基线但无实际充电责任”的场景，证明关闭窗口不会被错误拦截。
17. 作为测试人员，我希望能覆盖“自动策略已经参与主调度但缺少安全基线”的场景，证明真实调度责任仍会拦截关闭窗口。
18. 作为测试人员，我希望能覆盖 DO0 打开或激活场景，证明机构动作未收尾时不会放行关闭窗口。

## 实施决策

- 新增关闭窗口专用判断，命名为 `chargePileCloseInterceptionRequired()`，含义是“是否需要因充电安全拦截关闭窗口”。
- 该判断由设备管理层提供，设备管理层负责汇总当前充电控制器、自动会话、DO0、应用关闭流程和主调度参与状态。
- 保留充电控制器原有通用停机判断的保守语义，不在充电控制器中为关闭窗口场景放宽规则。
- UI 层只询问设备管理层是否需要拦截关闭窗口，不直接拼接充电状态业务规则。
- 自动充电协调器不作为本次主要修改点，避免把关闭窗口行为和自动策略实现继续耦合。
- 判断依据应区分两类事实：真实充电责任和安全事实。
- 真实充电责任包括：活动充电会话、自动会话未安全释放、DO0 打开或激活、应用关闭收尾进行中。
- 安全事实包括：控制器是否明确处于 `Fault` / `Unknown`，以及控制器是否仅缺少 `SafeComplete` 安全基线。
- “自动充电未开启”只取消自动策略造成的关闭绑定，不取消手动充电、历史残留、故障或未知状态带来的安全责任。
- “自动策略参与主调度”定义为：自动授权开启，且主调度状态不是 `Idle` 或 `Error`。

## 规则表

| 场景 | 关闭窗口行为 |
| --- | --- |

## 测试决策

测试应覆盖外部行为和规则结果，不测试 UI 内部实现细节。

优先采用最高测试切面：用纯规则函数覆盖关闭拦截规则表，再通过设备管理层的契约测试确认关闭窗口流程使用关闭窗口专用判断，而不是直接使用通用停机判断。

至少覆盖以下场景：

- 自动策略未参与，控制器仅缺少安全基线，没有真实充电责任：不拦截关闭窗口。
- 自动策略参与，控制器缺少安全基线：拦截关闭窗口。
- 存在活动充电会话：拦截关闭窗口。
- 自动会话未安全释放：拦截关闭窗口。
- DO0 处于打开或激活：拦截关闭窗口。
- 控制器处于 `Fault` / `Unknown`：拦截关闭窗口。
- 普通只读查询中，尚无 `Fault` / `Unknown`：不拦截关闭窗口。
- 启动轻量查询中，尚无真实充电责任：不拦截关闭窗口。
- 预检尚未进入 DO0 打开或激活：不拦截关闭窗口，但应取消预检意图，迟到结果不得继续启动充电动作。

同时需要一个契约检查：关闭窗口流程应调用关闭窗口专用判断，而不是直接使用通用充电停机判断。

## 不在范围内

- 不重写自动充电协调器。
- 不削弱充电控制器的安全保守策略。
- 不改变真实充电过程中的安全收尾要求。
- 不把 `Fault` / `Unknown` 当作可关闭状态。
- 不处理与本问题无关的调度策略、通信协议或 UI 重构。
- 不发布到项目 issue tracker；当前仓库未检测到可用的 issue tracker 配置或发布工具。
